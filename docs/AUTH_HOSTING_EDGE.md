The same-origin coverage issue is documented in
[AUTH_WEB_VALIDATION.md](AUTH_WEB_VALIDATION.md#firebase-reserved-route-coverage-limitation).
Firebase-managed `/__/auth/handler`, `/__/auth/iframe` and reserved SDK routes do
not receive the site's ordinary hosting headers. Firebase reserves `/__/*` for
its own features. The inspected baseline app does not depend on Firebase Auth or
the reserved SDK loader; this candidate denies that unused namespace. This is a
coverage correction, not a claim that those endpoints have been exploited.
[Firebase reserved URLs](https://firebase.google.com/docs/hosting/reserved-urls)

Cloudflare is currently authoritative DNS for this hostname, with the wallet

`fetch(request)` on such a route forwards to the existing DNS-defined origin.

## Reviewable candidate

Files are isolated in `tool/auth_release_gates/edge/`:

- `src/worker.js`: the module Worker; no runtime dependencies, bindings, secrets,
  request-body reads, response-body reads or custom logging.
- `wrangler.jsonc`: Worker `gleec-dex-reserved-paths`, exact route
  `dex.gleec.com/*` in `gleec.com`, no `workers.dev` or version-preview URLs.
- `package.json` / `package-lock.json`: pinned local validation tooling.
- `test/worker.test.js`: classification, boundary and object-preservation checks.
- `test/runtime.test.js`: actual local workerd with an in-process synthetic origin.
- `worker-configuration.d.ts`: generated by Wrangler, not edited by hand.

The only response created by production code is a reserved-path denial:

```http
HTTP/1.1 404 Not Found
Content-Type: text/plain; charset=utf-8
Cache-Control: no-store
X-Content-Type-Options: nosniff
Content-Security-Policy: default-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'

Not found.
```

HEAD receives the same status/headers with an empty body. Denied requests cannot
become redirects or upgrades. No CORS grant, cookie or HTML is returned.

The exact-host route covers all paths so encoded reserved paths cannot miss a
narrow `/__/*` route. Inside the Worker, classification is limited to the exact
hostname `dex.gleec.com`; previews, sibling hosts and lookalikes pass through if a
route is accidentally widened. Every accepted request is forwarded as the
original Request object, and the original upstream Response is returned. No
method, URL, body, cookie/auth header, status, redirect, cache header, streaming
body or WebSocket is rewritten by the Worker. Normal Cloudflare proxy behavior
can still add its own headers or apply existing zone rules; live comparison is
therefore required when enabling the proxy.
[Fetch passthrough behavior](https://developers.cloudflare.com/workers/runtime-apis/fetch/)

Classification considers repeated percent decoding, including escapes assembled
from adjacent encoded bytes, in linear time. It normalizes slash/backslash and
dot-segment interpretations for the decision only. Reserved interpretations with
matrix parameters, whitespace/control bytes or differing decode/traversal order
are denied conservatively. It never rewrites a forwarded path. `/__wallet`,
`/__.json`, nested `/wallet/__/…`, arbitrary query strings and deeply encoded
ordinary paths continue to the origin. The tests include 10,000 nested encoding
layers without imposing a decoding-depth limit on ordinary requests.
[Cloudflare URL normalization](https://developers.cloudflare.com/rules/normalization/how-it-works/)

Independent review caught a delimiter-order gap: decoded `?`/`#` can remain
literal path characters before traversal normalization. The final classifier
checks literal and delimiter interpretations and denies a reserved root exposed
at an intermediate traversal step, including mixed encoding depths. Seven added
regression variants pass in both the unit and local-runtime matrices. Review
found no further blocking code issue; no Firebase exploit was demonstrated.

The filter does not attempt to interpret nonstandard Unicode overlong encodings
as ASCII, invent legacy `%uXXXX` handling or promise compatibility with arbitrary
nonstandard origin decoders. Firebase and Cloudflare must continue to use their
documented URL behavior; the live bypass matrix checks the deployed chain.

The Worker does not call `passThroughOnException`. Route-level failure mode must
also be **fail closed**, particularly for quota exhaustion; that account setting
is not established by this local Wrangler file. Failure then affects availability
instead of exposing the blocked origin surface.
[Workers failure modes](https://developers.cloudflare.com/workers/platform/limits/)

Invocation logs and traces are disabled, query strings are redacted, and the code
does not log requests or errors. Remaining configured observability sampling is
1%; do not enable request logging or attach a tail consumer containing wallet
URLs during rollout.
[Workers invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)

## Rollback procedure

Keep the captured DNS/route/version state until the live checks are complete.
If a previous **protective** Worker version is known-good, restore that exact
version with `npx wrangler rollback <PREVIOUS_VERSION_ID>` and confirm its route
and failure mode remain intact. Worker version rollback does not restore DNS
records or route changes by itself.

For the first installation, if proxying or this route breaks the site, remove
only the newly created `dex.gleec.com/*` route (or restore the prior exact route
binding), then restore the captured `dex` DNS record to its original DNS-only
CNAME state. Do not change nameservers, the Firebase deployment, apex/sibling
records or the CNAME target. Verify the pre-edge content hashes and TLS again.
This restores prior availability **and reopens the reserved-route coverage
gap**; mark the browser security release gate blocked until the edge correction
is fixed and reapplied. Do not describe that rollback as security-complete.

No live activation, production proxy comparison, route-failure verification or
rollback rehearsal has been performed by this local preparation.
